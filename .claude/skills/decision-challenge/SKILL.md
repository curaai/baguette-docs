# 결정의 허점 검토
결정을 바꿀 만한 문제를 찾아 채팅에 보고한다.
검토만 요청받았으면 문서·태스크를 만들거나 수정하지 않는다.
수정까지 명시적으로 요청받았으면 공통 승인 규칙과 요청 범위를 따른다.

## 검토 범위
- 제작 비용이 큰 방향, 되돌리기 어려운 선택, 근거보다 확신이 앞서는 주장을 검토한다.
- 모든 기획에 검토를 의무화하거나 별도 승인 단계를 추가하지 않는다.
- 코드 리뷰나 문서 전체의 정합 검사를 대신하지 않는다.

## 진행
1. 검토할 결정과 대상 문서·초안을 한 문장으로 특정한다. 대상이 불분명할 때만 질문한다.
2. 의도한 플레이 경험, 유지할 조건, 근거와 미확인 가정을 구분한다. 관련 문서만 읽고 작성자의 자신감이나 권위를 증거로 삼지 않는다.
3. 결정을 뒤집을 만한 반례를 찾는다. 플레이어가 예상과 다르게 행동하는 장면, 정보가 전달되지 않는 경우, 반복 피로, 제작·검수 부담 중 해당하는 것을 살핀다.
4. 중요한 의심부터 실제 자료와 대조한다. 확인하지 않은 플레이 경험·구현 상태·공수는 사실로 쓰지 않는다. 플레이 테스트나 프로토타입 제작이 필요하면 확인 방법을 제안하고 실행을 대신하지 않는다.
5. 반례가 성립하는 조건, 영향과 근거를 함께 적는다. 단순한 취향 차이나 막연한 가능성을 치명적 문제로 부풀리지 않는다.
6. 우려마다 확인됨·반박됨·완화됨·미확인 중 상태를 밝힌다. 사용자가 명시적으로 받아들인 경우에만 남은 위험을 수용한 것으로 적는다.

## 판단과 종료
- 진행 가능: 방향을 바꿀 근거가 없고 남은 불확실성이 작다.
- 확인 후 판단: 결정에 중요한 근거가 비어 있다. 무엇을 확인하면 되는지 적는다.
- 방향 재검토 권고: 실제 반례나 조건 충돌이 의도한 경험을 무너뜨린다. 고칠 조건이나 작은 대안을 제안한다.

판단은 권고다. 사용자의 선택·승인을 대신하거나 다른 작업을 자동으로 막지 않는다.
한 차례 검토로 끝낸다. 새 근거나 수정안이 있을 때만 한 차례 더 검토한다.
두 차례 뒤에도 모르는 것은 미확인으로 남긴다. 같은 의심을 표현만 바꿔 반복하지 않는다.

## 채팅 출력
첫 문장에 판단과 이유를 적는다.
발견 사항은 문제·근거·제안으로 짧게 정리한다. 여러 항목을 비교하기 쉬울 때만 표를 쓴다.
영향이 큰 문제부터 적고, 근거가 약한 가정과 실제 확인 결과를 구분한다.
판단을 바꿀 확인 항목이 있으면 마지막에 적는다. 문제가 없으면 없다고 말한다.
별도 검토 보고서, 기억 저장소, 고정된 마무리 질문은 만들지 않는다.
