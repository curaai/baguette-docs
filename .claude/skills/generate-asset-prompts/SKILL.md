# 에셋 원화 프롬프트 작성

사용자가 원하는 이미지를 생성 도구에 전달할 수 있는 프롬프트로 만든다. 특정 프로젝트·장르·화풍·플랫폼·저장 방식은 전제하지 않는다.

## 요청과 범위

- 현재 요청과 대화에서 승인한 내용을 먼저 확인한다. 신규 디자인, 기존 이미지의 부분 수정, 변형 시리즈, 기존 프롬프트 변환 중 무엇인지 구분한다.
- 프롬프트 요청이면 이 스킬에서 완성한다. 실제 이미지가 결과물인 요청은 사용 가능한 이미지 생성 도구로 수행하며 프롬프트 파일로 대체하지 않는다. 둘 다 요청하면 둘 다 처리하되 생성 도구의 실제 지원 범위를 따른다.
- 키아트·실내외 장면도 처리할 수 있다. 별도 `generate-keyart-prompts`가 있고 공간·시점 설계가 필요하면 그 스킬의 관련 공간 지침만 참고한다. 보조 스킬의 프로젝트 고유 설정·기본 스타일은 현재 요청의 근거가 있을 때만 적용한다. 출력 형식이나 플랫폼 때문에 서로 넘기지 않고, 현재 요청을 맡은 쪽에서 완료한다. 별도 스킬이 없어도 진행할 수 있어야 한다.
- 개수는 컨셉 수, 이미지 수, 뷰 수, 변형 수, 파일 수를 구분한다. 예를 들어 한 이미지 안의 4뷰와 독립 이미지 4장은 다르다. 요청이 모호하고 결과가 달라질 때만 확인한다.
- 결과에 영향을 주는 방향·범위가 미정이면 공통 작업 규칙에서 정한 방식으로 필요한 선택을 묻는다. 별도 규칙이 없으면 사용 가능한 질문 도구나 채팅을 사용한다. 관련 질문은 함께 묶을 수 있다. 이미 승인된 방향과 저장은 다시 묻지 않는다.
- 플랫폼이 미지정이면 도구에 종속되지 않는 프롬프트를 작성한다. 특정 구문·모델·워크플로에 맞춘 변환이 필요할 때 대상 정보를 확인한다. 조명 문단 유무 같은 작성 형식만 정하려고 질문하지 않는다.

## 근거와 레퍼런스

- 사용자가 지정한 자료와, 프로젝트 목차가 있으면 그 목차에서 요청에 필요한 문서만 확인한다. Baguette 문서 저장소에서 작업할 때만 같은 스킬 폴더의 `references/baguette-context.md`를 읽어 로컬 관례를 적용한다.
- 이미지가 제공되거나 실제 근거로 사용할 때는 사용 가능한 이미지 보기 도구로 직접 확인한다. 도구 이름을 고정하지 않는다. 이미지가 없으면 텍스트에 근거한 신규 디자인을 작성할 수 있다.
- 이미지마다 참고 목적을 구분한다. 정체성·형태·재질·화풍·색·구도 중 지정된 요소만 가져온다. 구도 참고 이미지의 캐릭터나 배경을 디자인 요구로 옮기지 않는다.
- 최신 사용자 지시와 명시적으로 승인된 결정을 우선한다. 이미지와 문서는 각자 지정된 역할·승인 상태에 따라 사용하며, 이미지가 항상 문서보다 우선하지 않는다.
- 충돌이 결과를 바꾸고 우선순위가 정해져 있지 않으면 해당 부분을 확인한다. 의존하지 않는 조사·작성은 계속할 수 있다. 미정 값을 확정된 프롬프트처럼 전달하지 않는다.
- 필요한 원본을 열 수 없으면 확인하지 못한 내용을 관찰 사실처럼 쓰지 않는다. 원본에 의존하는 수정은 자료 확보까지 보류하고, 의존하지 않는 신규안은 구분한다.

## 프롬프트 구성

문단 순서와 길이는 작업에 맞춘다. 필요한 구성 예시는 같은 폴더의 `template.md`를 사용하되, 빈 항목을 채우기 위해 조건을 만들어 넣지 않는다.

1. **대상과 목적**: 무엇을 어떤 용도로 그리는지 구체화한다. 신규 디자인이면 요구 형태를 설명하고, 수정이면 보존할 요소와 변경할 요소를 나눈다. `exactly as-is`는 실제로 유지해야 하는 요소에만 적용한다.
2. **형태와 표현**: 실루엣·재질·색·화풍 중 요청과 근거가 요구하는 요소를 쓴다. 승인된 프로젝트 스타일은 반영하지만 스킬 자체에 특정 팔레트나 세계관을 고정하지 않는다.
3. **시점과 배치**: 필요한 뷰, 카메라, 구도, 개체 수, 배경 처리와 여백을 명시한다. 단독 에셋에 장면이나 주변 소품을 임의로 더하지 않는다.
4. **제작 조건**: 지정된 비율·해상도·투명 배경·타일링·뷰 간 일관성 등을 반영한다. 프롬프트에 적은 요청과 도구에서 별도로 설정해야 하는 값을 구분한다.

에셋별로 결과를 좌우하는 조건을 선택한다. 아래는 선택 기준이며 모든 행을 적용하는 체크리스트가 아니다.

| 대상 | 필요한 경우 구체화할 조건 |
|------|-------------------------|
| 캐릭터·턴어라운드 | 정체성, 포즈·표정, 지정한 각도, 전신 범위, 뷰 간 크기·디자인 일치 |
| 프롭·모듈 | 실루엣, 재료, 기능을 읽는 방향, 접지·결합부, 단독 배경 |
| UI·아이콘 | 작은 크기에서의 가독성, 외곽 여백, 세트의 선·명암·팔레트 일치, 배경 처리 |
| FX·스프라이트 | 동작 단계·방향, 프레임 배치, 배경 처리, 반복 여부 |
| 텍스처 | 표면과 무늬 크기, 반복 경계, 조명·투시 포함 여부 |
| 환경·키아트 | 공간 관계, 시선의 초점, 깊이, 장면에 필요한 빛과 분위기 |

- 색감·테마·무드·시간대는 명시된 요구나 승인된 근거가 있을 때 반영한다. 모든 에셋에 세 요소를 별도 문장으로 강제하지 않는다. 재질 확인용 중립광처럼 목적에 맞는 표현을 쓸 수 있다.
- 텍스트·라벨·워터마크·배경·추가 인물의 배제는 실제 요구에 맞춘다. 글자가 필요한 UI나 주석 시트에 `no text`를 기계적으로 붙이지 않는다.
- 버전 간 고정 요소와 변경 요소를 구분한다. 복사해 독립적으로 사용할 결과가 필요하면 완성 프롬프트를 각각 제공한다. 공통 베이스와 교체 문장은 사용자가 조합하는 형식을 원할 때 사용한다.

## 플랫폼에 맞추기

- 지정한 도구·모델에 필요한 형식으로 직접 작성한다. Nano Banana용 초안을 먼저 만드는 것을 다른 플랫폼의 선행 조건으로 삼지 않는다.
- Nano Banana 등 자연어 지시용 출력에는 대상·관계·수정 범위를 명료하게 쓴다. 레퍼런스가 있을 때만 업로드 대상과 역할을 안내한다. 요청하지 않은 모델 버전은 고정하지 않는다.
- ComfyUI 요청은 가능한 범위에서 모델·텍스트 인코더·워크플로를 확인한다. 이를 모르면 형식에 영향을 주는 정보만 질문하거나, 사용자가 범용 초안을 원하면 미확인 조건을 짧게 밝힌다. 모든 모델에 쉼표 태그가 우월하다고 가정하지 않는다.
- Positive/Negative 분리는 워크플로가 지원하고 필요한 경우에 사용한다. Negative에 에셋과 무관한 해부학 용어나 승인된 스타일과 충돌하는 상투어를 넣지 않는다. 지원 여부가 미확인이면 별도 필수 입력이라고 단정하지 않는다.
- 이미지 참조 방식과 조건 제어는 대상 워크플로에 맞춰 안내한다. 특정 노드를 보편적 필수 조건으로 지정하지 않는다. 노드 구성·설정 변경은 요청받았을 때만 한다.
- 다른 플랫폼도 같은 원칙을 적용한다. 최신 문법이나 지원 기능이 필요하고 확실하지 않으면 공식 자료로 확인한다. 지원되지 않는 출력 속성을 프롬프트만으로 보장하지 않는다.

## 전달과 확인

- 사용자가 지정한 언어·형식·경로를 따른다. 별도 형식 요청이 없으면 채팅에 바로 복사할 프롬프트를 제공한다. 언어 미지정 시 프롬프트는 영문, 설명은 사용자 언어로 작성할 수 있다.
- 파일 요청이면 지정 위치 또는 확인한 프로젝트 관례에 저장한다. 기존 결과와 충돌하면 별도 파일로 보존하거나 덮어쓰기 범위를 확인한다. 경로를 알 수 없고 프로젝트 관례도 없으면 저장 위치를 묻고, 그동안 본문을 준비한다.
- 단일 요청에 사용 안내 파일·폴더 묶음을 자동으로 추가하지 않는다. 여러 파일의 사용법이나 참조 대응이 필요할 때만 안내를 붙이고, 문서 목차는 해당 프로젝트의 README 규칙을 따른다.
- 최종 출력에서 요청한 대상·개수·뷰·변경 범위, 적용한 근거, 기술 조건과 배제 조건의 충돌을 확인한다. 제공하지 않은 이미지·파일을 참조하지 않는지 점검한다.
- 실제 프롬프트 블록에는 복사할 내용만 넣는다. 근거·사용법·미확인 조건은 밖에 둔다. 생성하지 않은 이미지나 실행하지 않은 워크플로를 검증했다고 표현하지 않는다.
- 마무리에는 결과 또는 저장 위치와 남은 중요한 제약만 짧게 알린다. 대안 평가를 요청하지 않았다면 우선 추천 컨셉을 의무적으로 추가하지 않는다.
