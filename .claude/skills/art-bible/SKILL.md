# 아트 바이블

원본 스킬을 이 저장소 경로와 작업 방식에 맞췄다. 출처는 에이전트·스킬 안내의 목차에서 관리한다.

아트 바이블은 **제약 문서**다. 앞으로의 시각 결정을 좁혀 주는 대신 일관성을 준다. 모든 섹션은 선택지를 좁히는 방향으로 쓴다.

## 경로

| 용도 | 경로 |
|------|------|
| 출력 (정본) | `foundation/art-direction.md` |
| 입력: 한 줄 약속·가격·장르 | `foundation/game-pitch.md` |
| 입력: 공포의 근원·감각 연출 | `foundation/horror-direction.md` |
| 입력: 프로토타입 장면 | `foundation/prototype.md` |
| 입력: AI 에셋 제작 흐름 | `foundation/ai-scene-asset-pipeline.md` |
| 입력: 구역별 비주얼 | `narrative/environment/**` |

이 vault를 단독으로 열면 위 경로가 루트 상대 경로다. 게임 레포의 `Docs/` 아래로 붙으면 앞에 `Docs/`를 붙인다.

## Phase 0: 컨텍스트 확인

1. **필러 확보.** 이 프로젝트에는 별도 필러 문서가 없다. `game-pitch.md`의 한 줄 약속과 `horror-direction.md`의 공포의 근원을 필러 대용으로 읽고, 추린 내용을 PD에게 한 번 보여 준다. 틀리면 PD가 고친다.
2. **기존 룩 문장 읽기.** `foundation/art-direction.md`를 통째로 읽는다. 이미 적혀 있는 문장은 해당 섹션 초안의 근거로 쓰고, PD 요청 없이 바꾸지 않는다.
3. **환경 문서의 비주얼 절 확인.** `narrative/environment/`에서 팔레트·라이팅·재질을 이미 정해 둔 문장을 찾는다 (`Grep`으로 `팔레트|조명|재질|안개|비네팅`). 이미 확정된 값은 새로 정하지 말고 해당 섹션 초안의 근거로 쓴다.
4. **파일 만들기.** `art-direction.md`에 `## 1.`~`## 9.` 제목이 없으면 첫 섹션을 승인받을 때 구조화된 질문 도구로 "`foundation/art-direction.md`를 아홉 섹션 구조로 바꿔도 될까요?"를 먼저 묻는다. 승인되면 아래 구조로 파일을 다시 쓴다. 기존 문장은 해당 섹션에 원문 그대로 옮기고, 나머지 섹션은 `[To be designed]`로 둔다. 이후 승인된 섹션이 자기 `[To be designed]` 줄을 `Edit`로 교체한다.

   ```
   # 아트 디렉션: Baguette
   > **Status**: Draft | **Owned By**: art-director | **Last Updated**: [날짜]

   ## 1. Visual Identity Statement
   ## 2. Mood & Atmosphere
   ## 3. Shape Language
   ## 4. Color System
   ## 5. Character Design Direction
   ## 6. Environment Design Language
   ## 7. UI/HUD Visual Direction
   ## 8. Asset Standards
   ## 9. Reference Direction
   ```
5. **이어서 쓰기.** 이미 아홉 섹션 구조이면 `Grep "\[To be designed\]"`로 남은 섹션만 찾아 그 섹션만 작업한다.

**승인 = 쓰기.** 모든 섹션은 구조화된 질문 도구의 `[A] 확정하고 foundation/art-direction.md에 쓰기` 선택으로만 파일에 반영된다. 승인 없이는 어떤 섹션도 쓰지 않는다.

## Phase 1: 프레이밍

작성 전에 구조화된 질문 도구로 두 가지를 묻는다.

- **범위**: "오늘 어떤 섹션을 작성할까요?"
  `전체 아홉 섹션` / `룩 코어 (1~4)` / `에셋 규격만 (8)` / `이어서 — 남은 섹션 채우기`
  이 프로젝트는 30분 분량의 소규모 게임이라 `룩 코어 (1~4)`를 (추천)으로 표시한다. 5~9는 1~4가 굳은 뒤 필요할 때 붙인다. 이유를 한 줄로 같이 말한다.
- **레퍼런스**: "비주얼 방향을 정하는 레퍼런스 게임·영화·작품이 있나요?" 자유 입력. 선택지를 미리 주지 않는다.

**선택한 범위의 섹션만 작성한다.** 범위 밖 섹션은 건너뛰고, Phase 6에서 건너뛴 섹션과 이유를 밝힌다.

## Phase 2: 비주얼 아이덴티티 기반 (섹션 1~4)

이 네 섹션이 룩의 핵심 언어이고 나머지는 여기서 나온다. 섹션마다 작성 → 승인 → 파일 반영을 마치고 다음으로 간다.

> **위임 정책.** 섹션 1은 단독으로 위임한다. PD가 방향 후보 중에서 고르기 전에는 다른 것이 쌓일 수 없다. 섹션 2~4는 `art-director` **한 번의 호출**로 위임한다. 무드·형태·색은 서로 얽혀 있어서 따로 쓰면 앞 결정을 모르고 색을 정하게 된다. 한 호출로 받아도 PD 승인과 파일 반영은 섹션 하나씩 한다.
>
> `art-director`는 **초안만 반환**한다. 파일 쓰기는 하지 않는다. 쓰기는 이 스킬이 PD 승인 후에만 한다.

### 섹션 1: Visual Identity Statement

**목표**: 시각적 모호함을 풀어 주는 **세계관 수준의 한 줄 규칙** + 보조 원칙 2~3개. 이 게임이 세계를 어떤 눈으로 보는지를 정한다. 원본 예: "모든 것은 움직여야 한다", "아름다움은 부패에 있다". 조명·색·형태·레퍼런스는 §2~4, 9에서 다룬다.

다룰 것:
- 방향 이름
- 한 줄 규칙 — 어떤 시각 결정에도 적용되는 하나의 입장
- 보조 원칙 2~3개 — 각각 이름, 디자인 테스트 한 문장("X가 모호하면 Y를 택한다"), 받치는 필러
- 시각 근거 — 이 게임의 구체적 장면 하나로 보인 모습

후보는 서로 **다른 방향**으로 2~3개 낸다.

**Agent delegation**: `art-director`를 `Agent`로 호출한다.
- 전달: 한 줄 약속, 공포의 근원, 필러 대용 요약, 플랫폼(PC / Steam), Phase 1 레퍼런스, 기존 룩 문장.
- 요청: "이 게임의 Visual Identity Statement 후보 2~3개를 작성하라. 후보마다 (1) 이름, (2) 모든 시각 결정의 모호함을 풀 세계관 수준의 한 줄 규칙, (3) 보조 원칙 2~3개 — 각각 'X가 모호하면 Y를 택한다' 형태의 테스트 한 문장과 받치는 필러, (4) 이 게임 장면 하나로 보인 시각 근거. 후보끼리 서로 다른 방향이어야 한다. 조명·가독성·레퍼런스는 쓰지 마라."

초안을 PD에게 보여 주고 구조화된 질문 도구: `[A] 확정하고 쓰기` / `[B] 한 줄 규칙 수정` / `[C] 보조 원칙 수정` / `[D] 내 방향을 직접 설명`

승인되면 바로 파일에 쓴다. PD가 후보를 이해하지 못하면 용어를 바꿔 설명하지 말고, 후보마다 이 게임의 실제 장면 한 컷에 적용한 모습으로 풀어 보여 준다.

### 섹션 2: Mood & Atmosphere

**목표**: 게임 상태별 감정 목표. 라이팅 담당이 바로 작업할 수 있을 만큼 구체적이어야 한다.

이 게임의 상태 후보: 낮(겉), 저녁, 밤(속), 폭우·추격, 새벽, 실내 문턱 전환. 상태마다 정의한다.
- 주 감정·무드 목표
- 라이팅 성격 (시간대, 색온도, 대비)
- 분위기 형용사 3~5개
- 에너지 수준 (측정된 / 관조적 / 몰아치는 등)

**섹션 2~4 위임 — 여기서 한 번만 호출한다.** `art-director`에게 확정된 섹션 1과 필러를 주고 한 번에 요청한다.

1. **무드·분위기** — "주요 게임 상태마다 무드 목표를 정하라. '어둡고 불길한'은 부족하다. 정확한 감정 목표, 라이팅 성격(따뜻/차가움, 고/저대비, 시간대 방향), 무드를 실어 나르는 시각 요소를 최소 하나 적어라. 상태끼리 시각적으로 구분돼야 한다."
2. **형태 언어** — "이 게임의 형태 언어를 정하라. 각 원칙을 비주얼 아이덴티티 문장과 특정 필러에 연결하고, 그 형태 선택이 플레이어에게 감정적으로 무엇을 전하는지 설명하라."
3. **색 체계** — "이 게임의 색 체계를 설계하라. 의미 기반 색 배정마다 이유를 설명하라(이 세계에서 왜 이 색이 위협/안전/보상인가). 색각 이상 플레이어에게 구분이 어려운 색 쌍과 필요한 보조 단서를 짚어라."

세 블록이 **서로 일관**되도록 요구한다(팔레트는 무드 목표와 형태 위계를 받쳐야 한다). 라벨이 붙은 세 블록으로 반환받는다.

그다음 **섹션 2만** PD에게 보여 주고, 승인받고, 파일에 쓴 뒤 섹션 3으로 간다. 세 개를 한꺼번에 보여 주지 않는다. 묶는 것은 위임이지 검토가 아니다.

### 섹션 3: Shape Language

**목표**: 이 세계를 시각적으로 일관되고 구별되게 만드는 기하 어휘.

- 캐릭터·존재 실루엣 철학 (썸네일 크기에서 읽히는가, 유형별 구별 특징)
- 환경 지오메트리 (각진/곡선/유기적/기하학적 — 무엇이 지배하고 왜)
- UI 형태 문법 (월드 미감을 따르는가, 별도의 HUD 언어인가)
- 주연 형태 대 조연 형태 (무엇이 시선을 끌고 무엇이 물러나는가)

위 2~4 위임의 형태 언어 블록을 쓴다. 다시 호출하지 않는다. 승인 후 바로 쓴다.

### 섹션 4: Color System

**목표**: 미감과 의사소통을 모두 받치는, 제작 가능한 팔레트 체계.

- 주 팔레트 5~7색과 역할 (HEX만이 아니라 이 세계에서 무엇을 뜻하는가)
- 의미 기반 색 사용 (붉은색은 무엇을 전하는가, 이 세계의 색 어휘)
- 구역·시간대별 색온도 규칙
- UI 팔레트 (월드와 다르면 갈라지는 지점을 명시)
- 색각 이상 안전성 (어떤 의미색에 형태·아이콘·소리 보조가 필요한가)

환경 문서에 이미 있는 팔레트(청록, 검은 갈색, 회색 화강암, 포인트 단청)는 출발점으로 쓰고, 역할과 수치를 붙인다. 2~4 위임의 색 체계 블록을 쓴다. 다시 호출하지 않는다.

## Phase 3: 제작 가이드 (섹션 5~8)

비주얼 아이덴티티를 구체적인 제작 규칙으로 옮긴다. 외주 팀이 추가 브리핑 없이 따라갈 수 있을 만큼 구체적이어야 한다.

### 섹션 5: Character Design Direction

**섹션 5~6 위임 — 여기서 한 번만 호출한다.** 둘 다 같은 입력(섹션 1~4)이 필요하므로 `art-director`를 한 번 호출해 둘을 함께 요청한다.

1. **캐릭터 디자인 방향** — "플레이어 캐릭터(취재하러 온 인물)의 시각 원형, 스님·원혼·검은 영혼 등 유형별 구별 규칙(한눈에 어떻게 구분하는가), 표정·포즈 스타일 목표(굳은/표현적/사실적/과장), LOD 철학(카메라 거리에서 디테일을 얼마나 남기는가)을 다뤄라. 공포 대상은 얼굴·형체를 얼마나 드러낼지 단계별로 정하라."
2. **환경 디자인 언어** — "건축 양식과 한국 사찰 문화·역사와의 관계, 텍스처 철학(페인팅 / PBR / 스타일라이즈 중 왜 이것인가), 구역 유형별 프랍 밀도 규칙(드문/빽빽 — 무엇이 정하는가), 텍스트 없이 이야기를 전하는 환경 스토리텔링 지침을 다뤄라."

캐릭터와 환경은 **서로에 대해 읽혀야** 한다. 캐릭터 실루엣이 같은 브리프가 정한 환경 텍스처 밀도 위에서 읽혀야 한다. 라벨이 붙은 두 블록으로 반환받는다.

**섹션 5를 먼저** 보여 주고 승인·쓰기를 마친 뒤 섹션 6으로 간다.

### 섹션 6: Environment Design Language

위 5~6 위임의 환경 블록을 쓴다. 다시 호출하지 않는다. 기존 `art-direction.md`의 확정 문장(near-photoreal, 열린 하늘 등)은 여기에 원문 그대로 옮긴다. 승인 후 쓴다.

### 섹션 7: UI/HUD Visual Direction

`art-director` 단독으로 작성한다. 다룰 것:
- 디제틱 UI(수첩 등 월드 안 물체) 대 스크린 공간 HUD
- 타이포 방향 (서체 성격, 굵기, 크기 위계, 최소 가독 크기)
- 아이콘 스타일
- UI 애니메이션 느낌

아트 방향과 가독성·접근성이 충돌하는 지점은 **조용히 정리하지 않는다.** 두 입장을 모두 적고 구조화된 질문 도구로 PD가 결정하게 한다. 승인 후 쓴다.

### 섹션 8: Asset Standards

`art-director` 단독으로 작성한다. 다룰 것:
- 파일 포맷, 네이밍 규칙 (`[category]_[name]_[variant]_[size].[ext]`), 텍스처 해상도 등급, LOD 기대치, 익스포트 설정 철학
- `foundation/ai-scene-asset-pipeline.md`의 A/B/C 등급과 패밀리 단위 제작 원칙을 규격에 연결

**기술 한계는 추정하지 않는다.** 엔진(Unity)의 폴리 예산, 텍스처 메모리, 머티리얼 슬롯 한계는 이 저장소에 문서가 없다. 구조화된 질문 도구로 PD에게 목표값을 묻거나, 값이 없으면 `[미정]`으로 남긴다. 아트 선호와 기술 한계가 충돌하면 이상적 기준, 제약된 기준, 둘 다 기록하고 에셋별 판단에 맡기는 안 중에서 PD가 고르게 한다. 에셋 규격의 모호함에서 제작비가 샌다.

## Phase 4: 레퍼런스 방향 (섹션 9)

**목표**: 각 출처에서 **무엇을 가져오고 무엇을 피할지** 구체적으로 적은 레퍼런스 세트.

`art-director`에게 완성된 섹션 1~8을 주고 요청한다: "이 게임의 레퍼런스 방향을 정리하라. 출처 3~5개(게임, 영화, 화풍, 작가)마다 이름, 가져올 구체적 시각 요소('전반적 미감'이 아니라 특정 기법·색 선택·구도 규칙), 피하거나 벗어날 것('X를 베낀 것'으로 읽히지 않도록)을 적어라. 레퍼런스끼리 같은 방향을 가리키지 않게 하라. 한국 사찰의 실제 단청·기와·석물 실사 사진 출처를 최소 하나 포함하라."

승인 후 쓴다.

## Phase 5: 마무리 점검

모든 섹션(또는 Phase 1 범위)이 끝나면 PD에게 다음을 확인받는다.

- 색 체계가 무드 목표와 맞는가
- 형태 언어가 비주얼 아이덴티티 문장에서 나오는가
- 에셋 규격이 플랫폼 제약 안에서 달성 가능한가
- 섹션 간 모순이 없는가
- `[미정]`이 남은 곳이 어디인가
- 헤더의 `Status`를 `Draft` / `Under Review` / `Approved` 중 무엇으로 둘까 (구조화된 질문 도구)

`Last Updated`를 오늘 날짜로 갱신한다.

## Phase 6: 마무리와 다음 단계

먼저 이번에 작성하지 않은 섹션과 이유를 적는다. 예: *"이번에 작성하지 않은 섹션: 5~9 (선택한 범위 밖)."* 섹션 4에서 멈춘 실행이 완성된 문서처럼 읽히면 안 된다.

다음 단계는 구조화된 질문 도구로 묻는다. 실제로 이어지는 것만 넣는다.

- `환경 문서 정리` — `narrative/environment/`의 팔레트·라이팅 중복 문장을 정본(art-direction)과 대조해 구역별 차이만 남기자고 제안
- `에셋 원화 프롬프트` — `generate-asset-prompts`로 이어서 프랍·캐릭터 원화
- `키아트·배경 프롬프트` — `generate-keyart-prompts`로 이어서 장면 배경
- `여기서 멈추기`

이미 끝난 것은 제외하고, 가장 자연스러운 하나에 (추천)을 붙인다.

## 협업 프로토콜

모든 섹션은 **질문 → 선택지 → 결정 → 초안(art-director) → 승인 → 파일 반영** 순서를 따른다.

- 섹션 내용을 이 스킬이 직접 쓰지 않는다. 모든 섹션의 내용은 `art-director`에서 나온다. 한 번의 위임이 여러 섹션을 덮을 수 있다(2~4, 5~6). 섹션 7, 8도 `art-director`가 쓴다.
- 승인된 섹션은 **즉시** 파일에 쓴다. 쓰기와 승인은 묶지 않는다. 묶는 것은 위임 호출뿐이다.
- 방향이 갈리는 결정, 충돌, 범위는 모두 구조화된 질문 도구로 묻는다. 일반 텍스트로 승인 질문을 하지 않는다.
- 확정되지 않은 값은 `[미정]`으로 남긴다. 추정으로 채우지 않는다.
- 문서 본문에 다른 문서로 가는 `## 참고` 섹션이나 인라인 링크를 만들지 않는다. 문서 발견은 폴더 `README.md`의 표가 맡는다.
- 이미 파일에 있는 확정 문장을 PD 요청 없이 바꾸지 않는다.
