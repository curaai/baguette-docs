# Auto Commit

* 저장소 변경 내용을 확인하고 실제로 커밋한다.
* Commit Message는 항상 한국어로 작성한다.
* `어떻게`보다 `왜`에 집중한다.
* Description은 최대한 간략하고 압축해서 작성한다.
* 커밋 명령어를 사용자에게 제시하지 않고 직접 실행한다.
* 커밋 완료 후 커밋 메시지와 결과만 간략하게 알린다.
* Dotted list는 3개를 초과하지 않는다.

## Workflow

1. 사용자가 지정한 파일과 이미 스테이징된 변경을 우선 확인한다.
2. 관련 없는 변경은 커밋에 포함하지 않는다. 커밋 범위가 불명확하면 먼저 확인한다.
3. 변경 이유에 맞는 Header와 필요한 경우에만 Body, Footer를 작성한다.
4. 필요한 파일만 스테이징하고 `git commit`을 직접 실행한다.
5. 커밋 성공 여부와 생성된 커밋을 간략하게 보고한다.

## Scope

* 이 규칙의 `type(scope): 제목` Header는 **git commit message에만** 적용한다.
* **PR 제목**에는 `type(scope):` / `type(주제):` 접두어를 넣지 않는다. 제목 본문(왜/목적) 만 쓰는다.
* 예: 커밋 `fix(format): IDE1006 FixAll 스팸을 막고 UNT206으로 접두사 규칙을 맡긴다` → PR 제목 `IDE1006 FixAll 스팸을 막고 UNT206으로 접두사 규칙을 맡긴다`

## Structure

```text
// Header, Body, Footer는 빈 행으로 구분한다.
타입(주제): 제목 // Header

본문 // Body

참조 정보 // Footer
```

* Header는 반드시 `type(scope): 제목` 형식을 사용한다.
* `type`은 커밋의 성격을 나타내며 다음 중 하나만 사용한다.

  * `feat`, `fix`, `build`, `chore`, `ci`, `docs`, `style`, `refac`, `test`, `asset`, `data`

* `scope`는 변경된 기능, 모듈 또는 작업 범위를 간결하게 작성한다.
* 제목은 변경한 내용보다 변경한 이유와 목적이 드러나도록 작성한다.
* Body는 Header만으로 설명이 부족한 경우에만 작성한다.
* Footer는 관련 이슈 번호 등 참조 정보가 있을 때만 작성한다.
* 주제는 한단어 정도로 간결하게 작성한다.

## Type Classification

* `asset`은 이미지, 사운드, 영상, 폰트, 모델, 애니메이션 등 에셋 파일의 추가, 교체, 삭제 또는 최적화에만 사용한다.
* 레벨 디자인 데이터, 밸런스 데이터, 설정 데이터, 테이블 데이터 변경에는 `asset`을 사용하지 않는다.
* 데이터 변경은 목적에 따라 다음과 같이 분류한다.

* asset: 이미지, 사운드, 모델, 애니메이션 등 리소스 파일
* data: 레벨, 밸런스, 테이블, 설정, 드롭률, 스폰 정보 등 데이터
* feat: 코드 기반 신규 기능
* fix: 코드·데이터를 포함한 오류 수정

## Example

```text
feat(matchmaking): 대기 시간 완화를 위해 매칭 범위 확장

장시간 대기 중인 사용자를 대상으로 검색 범위를 단계적으로 확대
```
