# TaskNotes — 작업 관리
지금 할 일과 진행 중 작업의 재개 정보를 관리한다.
기획의 체험·의도는 기획서에, 실제 동작은 코드에 둔다. 별도 `specs/` 문서나 현재 구현 스냅샷을 만들지 않는다.

## 저장 경로와 보기

| 항목 | 값 |
|------|-----|
| Vault 루트 | 이 저장소의 루트. Obsidian에서도 이 폴더를 연다. |
| 새 태스크 경로 | `TaskNotes/Tasks/<context>/<제목>.md` |
| TaskNotes의 tasksFolder 설정 | `TaskNotes/Tasks/{{context}}` |
| 슬라이스 묶음 | `contexts`로 관리. 관련 태스크와 요청에서 확인한다. |
| 부모 태스크 | `projects`를 사용. 슬라이스 묶음에는 쓰지 않는다. |

Obsidian의 Bases와 TaskNotes를 켠다. 저장 경로는 실제 플러그인 설정과 맞춘다.

## 태스크 작성
태스크 생성과 기획의 작업 분해는 `create-tasknote` 스킬을 쓴다.
제목·저장 경로·속성·본문을 채팅에서 보여 주고, 승인된 초안만 저장한다.
기존 태스크가 같은 작업을 다루면 새 태스크를 중복 생성하지 않는다.
context가 비어 있거나 후보가 여러 개면 질문한다. 예전 슬라이스 값을 고정해서 넣지 않는다.

| 속성 | 규칙 |
|------|------|
| `status` | 신규는 `todo`. 허용 값은 `todo`, `in-progress`, `done`, `archived` |
| `priority` | `lowest`, `low`, `medium`, `high`, `highest` 중 하나 |
| `tags` | `task`와 분야 하나만 사용: `기획`, `아트`, `프로그래밍` |
| `contexts` | 확인한 슬라이스·실행 묶음. 폴더의 context와 맞춘다. |
| `projects` | 부모 태스크가 있을 때만 사용. 기존 관계 속성 형식은 유지한다. |

본문은 목표, 작업, 완료 기준을 적고 필요할 때 범위 밖을 둔다.
할 일은 태스크에서 관리하고 기획서 본문에 쌓지 않는다.
기획서에 없는 새 게임 규칙이나 코드 구조를 작업 분해 과정에서 만들지 않는다.
다른 문서와의 연결은 이 README의 목차 표에서 관리한다. 태스크 본문에 문서 링크를 추가하지 않는다.
기존 태스크의 상태·우선순위·관계 속성을 문서 정리만으로 바꾸지 않는다.

## 결정 반영과 작업 재개
확정된 체험·서사·아트 방향과 필요한 선택 이유는 해당 문서의 기존 구성에 반영한다.
기획서는 의도와 기획 본문을 갱신한다. 탈락안 전체나 채팅 전문을 쌓지 않는다.
작업이 중단되거나 인계될 때, 관련된 기존 `in-progress` 태스크에 아래 재개 정보를 남긴다.
확인한 사실만 적고, 달라졌을 때 갱신한다. 기록을 위해 태스크를 자동으로 만들지 않는다.

```text
확정: 사용자가 승인한 내용
확인: 실제로 끝낸 작업과 확인 결과
미결: 아직 답이 필요한 사항
다음: 이어서 할 행동 한 가지
```

모르는 내용은 미확인으로 적는다. 날짜만 보고 승인·완료를 추정하지 않는다.
재개할 때는 해당 태스크의 목표·완료 기준·재개 정보를 읽고 필요한 문서를 찾는다.
`todo`는 예정 작업, `in-progress`는 진행 작업이다. `done`·`archived`는 이력으로만 본다.
현재 구현을 확인해야 하면 코드를 다시 본다. 완료 태스크를 현재 구현의 증거로 쓰지 않는다.
